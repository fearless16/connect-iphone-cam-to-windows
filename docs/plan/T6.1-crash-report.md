# T6.1 Crash report to the PC: mini-plan

Owner request (2026-11-26): when the phone connects over USB or Wi-Fi, send the
last crash report to the PC so it can be debugged. Must not bloat the phone or
cost performance. The owner delegated the transport choice.

## Decision

A **separate side channel on port 12347**, not a new packet type on 12345.
- No change to the video wire format (R-ARCH-2/D3): no header, golden-vector or
  parity change, and no risk to the 4K60 path.
- The listener exists **only while an undelivered report is waiting**. In normal
  use nothing listens and nothing runs.
- Same exposure rule as the stream (D4/G7 option A): USB only unless the Wi-Fi
  switch is on.

## Design

**Phone**
- `ios/CrashReportStore.swift` (Foundation only): framing (`ICRP` magic, u32 LE
  length, JSON, max 256 KiB), one file in Caches, newest report replaces older.
  `envelope` adds app/OS/device/time and shrinks oversized diagnostics.
- `ios/CrashReportService.swift`: MetricKit subscriber (`MXDiagnosticPayload`,
  crash diagnostics only; delivered on the next launch, so zero work while
  streaming). Serves the file on port 12347 and deletes it only after the PC
  sends the ack byte `0x06`. A stalled peer is cut off after 15 s.
- `CameraStreamer` owns the service and forwards the Wi-Fi choice and stop.

**PC**
- `windows/crash_report.h` (pure): header parse (magic, length 1..256 KiB) and
  a safe file name.
- `receiver.cpp`: when a session starts, one detached thread connects to port
  12347 (usbmux, then USB-network fallback, or `<host>:12347` for Wi-Fi), reads
  the header, validates it **before allocating**, reads the payload, saves
  `crash-reports\crash-YYYYMMDD-HHMMSS.json` next to the exe, then sends the ack.
  A phone with nothing pending refuses the connection and the thread ends.

## Not in scope
- Hangs, CPU exceptions and metrics (only crashes), and a log history.
- Authentication (G7 option A), and any change to the video protocol.

## Acceptance criteria
- AC1 [local] `crash_report_test` passes; `crash_report_source_contract.sh` passes.
- AC2 [local] `receiver.exe` links, and against a fake phone it saves a valid
  report and acks it, and rejects a bad magic and a 4 GiB length without acking.
- AC3 [CI] `crash_report_store_test` passes and the IPA builds.
- AC4 [device, owner] after a real crash and relaunch, the next connection
  produces a file in `crash-reports`. iOS may delay or withhold MetricKit
  reports (for example if analytics sharing is off), so a missing file is not
  proof the feature is broken: check Settings > Privacy > Analytics first.
