# T3.3 Wi-Fi discovery (Bonjour): mini-plan

Task: `feat/wifi-discovery` · Gate G7 option A (APPROVED) · deps T3.1 (DONE).
Goal: `receiver.exe --wifi` finds the phone on the LAN without typing an IP.

## Design

**Phone (`ios/StreamSender.swift`, `ios/Info.plist`)**
- In `startOnQueue`, when `wifiEnabled`, set
  `newListener.service = NWListener.Service(name: nil, type: "_ipcamstream._tcp")`.
  The listener is already rebuilt whenever Wi-Fi mode changes (T3.1), so the
  advertisement exists only while Wi-Fi mode is on. No new state.
- `Info.plist`: `NSBonjourServices` = `["_ipcamstream._tcp"]`.

**PC (`windows/wifi_discovery.h` pure, `windows/receiver.cpp` I/O)**
- Pure unit `wifi_discovery.h` (C++ std only, R-ARCH-4) validates untrusted LAN
  data before the receiver connects to it (R-ENG-INPUT):
  - `IsIpcamstreamInstanceName(name)`: must end with `._ipcamstream._tcp.local`,
    have a non-empty instance part, be at most 255 bytes, and be printable ASCII.
  - `FormatDiscoveredIPv4(octets, port, expectedPort)`: returns the dotted
    string, or nothing when the port is not 12345, or the address is
    unspecified (0.x), loopback (127.x), multicast or reserved (224 and up).
- `receiver.cpp` uses the Windows DNS-SD API (`DnsServiceBrowse`, then
  `DnsServiceResolve`) from `dnsapi`. It is a system library, so there is no new
  dependency. Verified on this PC: mingw `windns.h` declares both calls, and a
  probe linked with `-ldnsapi` and ran (browse returned `DNS_REQUEST_PENDING`).
- Callbacks run on system threads. They write into one static state guarded by a
  mutex and tagged with a generation number, so a callback that fires after a
  cancel or a timeout cannot touch freed memory or a newer attempt.
- `run_receiver` re-runs discovery on every connection attempt in `--wifi` mode,
  because a DHCP lease may change the phone's address. A failed or empty
  discovery is a normal retry (R-ENG-ERR), never an exit. Waits are sliced and
  honor `g_stopRequested`.
- CLI: `--wifi` discovers. `--host <addr>` wins if both are given. `--wifi` with
  a positional USB host is a usage error.

## Not in scope

- No wire-format change (D3). Port stays 12345, and the relay stays loopback-only.
- No `--latency-ms` change: T5.6 is not merged, so there is nothing to default.
- No authentication (G7 option A).

## Acceptance criteria

- AC1 [local] `wifi_discovery_test` passes: valid names and addresses accepted;
  wrong suffix, empty instance, over-long, non-ASCII, wrong port, 0.x, 127.x,
  224+ rejected.
- AC2 [local] `receiver.exe` still links with the MSYS2 g++ line used by CI (plus `-ldnsapi`).
- AC3 [local] source contracts pin: the browse and resolve calls, `--wifi`,
  `--host` precedence, and the sender's `service` line and plist key.
- AC4 [CI] the IPA builds and the plist key is present.
- AC5 [device, owner] with Wi-Fi mode on, `receiver.exe --wifi` finds the phone
  and streams. With Wi-Fi mode off, `--wifi` finds nothing and keeps retrying.
